# 0001. 资源管理自研，qanvas 掌握执行路径

- 状态：已接受
- 日期：2026-10-25
- 相关：[q-0001](../questions/q-0001-资源管理工具自研还是依托第三方.md)、[q-0002](../questions/q-0002-连接信息分发还是代执行.md)、[q-0003](../questions/q-0003-qanvas部署形态.md)

## 背景

- 面向 QA 的自建平台，数据校验 / 验证是高频操作。
- 需要集中维护数据库、消息中间件的连接信息。
- 需要按 QA 与 AI 两类主体做权限隔离和审计，重点是防止 AI 误操作造成破坏。
- 候选：自研 / Navicat / DBX。

## 决策

自研资源注册中心与执行路径；不把 Navicat / DBX 作为 source of truth、信任边界或平台调用链的一环。

组件划分：

- **qanvas**：面向 QA 的桌面应用，同时承担资源注册、策略判断、执行与审计（执行网关）。
- **qcore**：AI 使用的 CLI，只调用 qanvas 接口，不直接持有资源凭据。
- 第三方客户端只用于人工排查，不进入自动化调用链。

## 备选方案

- **Navicat**：无公开的编程接口，命令行只能拉起 GUI；无法作为平台后端。
- **DBX (t8y2/dbx)**：有 CLI / 自托管 Web API，但仍是 0.x、仅覆盖数据库、列表接口不输出密钥、多用户 / RBAC 不明确；其 MCP 权限模式不能替代平台自己的审计边界。
- **混合（DBX 做后端 + qanvas 做前端）**：用户无感，但仍受 DBX 的覆盖范围、契约稳定性和审计能力限制；qanvas 仍要自己解决 MQ 与统一审计，收益不足以抵消耦合。

## 后果

- qanvas 需要自己维护资源模型、接口契约和执行网关。
- 换来自有的权限模型、统一审计和 MQ 覆盖；凭据不必分发给 AI。
- qanvas 成为关键路径，需要关注可用性、超时与故障隔离。
- qcore 的客户端护栏只是 UX 兜底；AI 可以绕过 CLI 直接调 API，因此策略必须在 qanvas 服务端执行。
