# 资源管理工具：自研还是依托第三方？

需要集中维护数据库、消息中间件的连接信息，并对外提供接口，供后续 CLI 工具调用。应该自研，还是依托 Navicat / DBX 这类现成软件？

- 状态：已解答
- 日期：2026-10-25
- 相关：[目标与范围](../00-vision.md)

## 背景

- 管理对象：数据库连接池、消息中间件连接池的信息。
- 使用方式：在一处维护，提供接口，供后面的命令行工具调用。
- 使用方：面向 QA（测试开发工程师）的自建平台；数据校验 / 数据验证是高频操作。
- 安全要求：按 QA 与 AI 两类主体做权限隔离和审计，重点是审计 AI 执行的命令，防止误操作造成破坏。
- 候选方案：自研 / Navicat / DBX。

## 先厘清问题

这其实不是同一类东西的比较：

- **你要的是**：机器可读的资源注册中心 + 稳定接口（source of truth）。
- **Navicat / DBX 是**：给人用的数据库客户端。

两者都"保存连接信息"，但前者优化可编程访问，后者优化交互体验。拿客户端当后端，等于把它的内部存储当成公开 API。

## 候选对比

| | 自研薄注册中心 | Navicat | DBX (t8y2/dbx) |
| --- | --- | --- | --- |
| 定位 | 资源注册 + API | 商业 GUI 客户端 | 开源数据库客户端 |
| 程序化接口 | 自己定义，稳定 | 无官方 CLI / 公开 API | CLI `dbx connections list --json`；Web API `/api/connection/list` |
| 覆盖范围 | 数据库 + MQ + 任意资源 | 数据库 | 100+ 数据库；不含 Kafka / RabbitMQ 等 MQ |
| 凭据 | 自己接密钥管理 | 本地 / 云同步 | 加密存储；CLI 列表不输出密钥 |
| 人工界面 | 需另做 | 强 | 强 |
| 成熟度 | 取决于投入 | 成熟但封闭 | 0.x，API 与数据模型可能变化 |
| 多用户 / RBAC | 自己控制 | 不适用 | 不明确，偏单实例 |

## 关键判断

1. **调用方要凭据吗？** 如果 CLI 工具要自己建连接池，就必须拿到凭据；DBX CLI 的列表接口不输出密钥（Web API 是否暴露未验证，也不应依赖），因此它只能作为"执行器"（`dbx query`），不能作为"配置源"。
2. **只有数据库吗？** 如果还要 Kafka / RabbitMQ，DBX 覆盖不到，最终仍要自研或再加一套。
3. **"连接池信息"指什么？** 如果包含 min / max / idle 等池参数，DBX / Navicat 的模型是"连接"，不是"连接池"，领域也不匹配。
4. **个人还是团队？** 团队共享需要认证、权限、审计；DBX 自托管目前更像单密码实例。
5. **是否真的需要服务？** 单机、单语言时，一个私有配置文件 + CLI + 系统钥匙串就够了；跨机器 / 跨语言再上 HTTP 服务。

## 2026-10-25 补充：审计要求改变了问题

平台的审计对象是"执行"，不是"发放"。如果 AI 能直接拿到连接信息，它就可以绕过平台连库，平台既无法审计"执行了什么"，也无法阻止 DDL / DELETE 等破坏性操作。因此：

- 第三方客户端（Navicat / DBX）不能成为信任边界；DBX 的 MCP 权限模式也不能替代平台自己的审计。
- 资源注册中心之外，还需要执行网关：qanvas 负责策略、执行与审计，AI 通过 qcore 调用它的接口，凭据不出平台。
- QA 与 AI 要作为不同主体做权限隔离：AI 默认只读、资源 allowlist、写操作审批；QA 如需直连，应使用短期、最小权限凭据。

## 倾向

建议自研**薄**注册中心 + 执行路径，但不要自研连接池和数据库客户端：

- 核心投入放在资源数据模型与 API 契约，而不是 UI。
- 第一版：YAML / JSON 定义 + CLI（如 `qrc get <resource> --json`），密钥只存引用（OS Keychain / Vault / SOPS），不入库、不入 Git。
- 出现多机器或多个工具消费时，再把同一模型包一层 HTTP API + SQLite / Postgres。
- Navicat / DBX 留给人工浏览和排查，不作为机器调用的 source of truth；DBX 不进入 QA 工作流，也不进入平台调用链。

会改变这个建议的条件：

- 只需要数据库，且调用方接受"委托 DBX 执行查询"、不需要自己建池 → DBX 自托管很划算。
- 团队只需要一个共享的连接浏览器，不需要程序化接口 → DBX 足够。

## 待确认

- [ ] 平台"校验连接信息"是指连通性 / 凭据有效性校验，还是要把连接信息返回给调用方？
- [ ] QA 的 CLI 是否必须直连数据库 / 消息中间件？能否接受通过 qanvas 执行？
- [ ] AI 的写操作如何分级：一律人工审批，还是按资源 / 环境分级？
- [ ] 审计日志存在哪里、保留多久、是否需要防篡改？
- [ ] 是否包含消息中间件？具体是 Kafka / RabbitMQ / RocketMQ？
- [ ] 凭据放在哪里？是否已有 Vault / 1Password / KMS？
- [ ] qanvas 是单机桌面应用还是团队共享服务？

## 结论（2026-10-25）

已定案：自研。qanvas 提供本机注册与执行网关，qcore 作为 AI 侧只读 CLI；DBX 不进入调用链。执行模型见 [q-0002](q-0002-连接信息分发还是代执行.md)，部署形态见 [q-0003](q-0003-qanvas部署形态.md)，决断见 [ADR 0001](../decisions/0001-资源管理自研注册中心与执行路径.md) 与 [ADR 0002](../decisions/0002-v1本机网关与AI只读.md)。
